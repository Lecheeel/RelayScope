# 中转站掺水检测方案与讨论记录

> 本文记录项目方向调整的背景、讨论过程、用户原话、项目意图与后续设计期望，作为未来新分支“推倒重做”的需求基线和设计依据。

## 一、项目初衷

本项目的真正目的不是测试某个 API 是否“能调用”，也不是覆盖尽可能多的模型或工具，而是检测 **AI 中转站是否存在掺水行为**。

这里的“掺水”包括但不限于：

- 实际使用的模型与中转站声明的模型不一致；
- 请求参数被删除、修改或强制覆盖；
- Codex、Claude 的工具调用、流式协议或错误处理被削弱、转换或伪造；
- 使用缓存或响应复用伪装真实模型调用；
- 在特定请求、负载或上下文长度下发生模型降级或路由替换；
- 返回看似成功的结果，但实际没有按照官方接口的语义和能力执行。

项目应围绕上述目标设计证据链，而不是泛化成通用 API 能力测试工具。

## 二、用户原话

### 对统计与缓存分析的补充

## 三、已达成的共识

### 1. 检测对象严格限定

只检测两个常用工具/API 生态：

- Codex
- Claude

其他模型、其他工具和泛化 API 能力不属于本项目的核心检测范围。以后如果出现扩展需求，也不能牺牲这两个目标的检测准确性。

### 2. 以官方接口作为基准

检测必须建立“官方行为基线”与“中转站行为”之间的可重复对照，而不是只看中转站能否返回文本。

对于同一组测试请求，应尽可能在相同条件下分别访问官方接口和中转站，并记录完整交互，以便进行差分分析。

### 3. 先记录完整交互，再进行统计比较

“先抓包”的具体含义是记录客户端与 API 之间的完整 HTTP 交互，包括请求、响应以及流式事件。普通 HTTPS 网络监听通常无法直接看到正文，因此实现上可采用：

- SDK 请求拦截器；
- HTTP middleware；
- 本地代理或 TLS 终止点；
- 测试客户端内置的请求/响应记录器；
- 对 SSE/流式协议保存原始事件序列。

原始记录应可追溯、可重放，并保留敏感信息脱敏后的证据。

### 4. 不能以单次文本差异下结论

模型输出存在正常随机性。一次请求返回不同文本，不能直接证明中转站掺水；一次请求返回相同文本，也不能直接证明存在缓存。

结论必须结合：

- 多次重复实验；
- 固定和可控的请求条件；
- 协议字段差异；
- 响应分布；
- 延迟和 usage 数据；
- 缓存命中与复用特征；
- 统计显著性和置信度。

## 四、建议的证据维度

### 4.1 协议一致性

比较官方与中转站的：

- 请求字段和响应字段；
- 模型标识；
- 工具调用结构；
- 流式事件类型、顺序和结束事件；
- `finish_reason` 或等价字段；
- `usage`、token 统计及计费相关字段；
- 错误类型、错误码和错误消息结构。

### 4.2 参数完整性

重点检查系统提示词、消息内容、上下文、工具定义、温度、最大输出长度、随机种子、响应格式等是否：

- 被删除；
- 被修改；
- 被强制覆盖；
- 在官方支持但中转站不应修改的情况下发生隐式转换。

### 4.3 能力一致性

使用固定测试集和多次重复请求，比较 Codex/Claude 在以下场景中的行为：

- 工具调用；
- 多轮上下文；
- 长上下文；
- 复杂推理或代码任务；
- 结构化输出；
- 边界条件和错误请求。

能力测试用于发现模型替换或降级，但不应脱离协议和统计证据单独判定。

### 4.4 缓存与响应复用特征

不能只重复发送完全相同的请求。应设计对照组，分别改变：

- request ID；
- 无意义的 metadata；
- 消息中的随机 nonce；
- 请求时间；
- 不影响任务目标的参数；
- 上下文中可控的无关扰动。

记录并统计：

- 完全相同响应率；
- 语义相似度分布；
- 首 token 延迟和总延迟；
- usage 是否随请求变化；
- 流式事件是否被直接复用；
- 不同扰动下的缓存命中率。

### 4.5 模型替换或降级特征

结合输出分布、延迟、上下文上限、工具调用成功率、错误模式、流式协议和长上下文表现，判断实际路由模型是否可能与声明型号不同。

## 五、实验与统计原则

1. **固定变量**：测试集、请求参数、工具定义、系统提示词和上下文应尽量固定。
2. **显式记录变量**：每次实验记录时间、请求版本、客户端版本、模型声明、测试条件和原始响应。
3. **设置对照组**：官方接口、中转站接口、相同请求的重复组、带扰动请求组。
4. **重复采样**：单次结果只作为样本，不作为结论；需要足够重复次数观察分布。
5. **区分相关性与因果性**：响应相同、延迟降低或 usage 不变只能作为证据，不能自动等同于缓存或模型替换。
6. **输出置信度**：结论应包含证据强度、样本量、可能的替代解释和不确定性。

## 六、建议的结论格式

不要只输出武断的“掺水/没掺水”。建议分别报告：

- 协议一致性：高 / 中 / 低；
- 参数篡改风险：高 / 中 / 低；
- 缓存或响应复用证据：强 / 中 / 弱；
- 模型替换证据：强 / 中 / 弱；
- 模型降级证据：强 / 中 / 弱；
- 统计置信度与样本量；
- 支持结论的原始证据和差异摘要；
- 可能的替代解释。

示例：

> 协议一致性：高。参数篡改风险：中。缓存复用证据：强。模型替换证据：弱。综合结论：存在缓存或响应复用嫌疑，但现有样本不足以证明发生模型替换。

## 七、未来新分支的设计边界

未来新分支可以直接重新设计，不必受现有检测器结构束缚。建议按以下四层组织：

1. **实验协议层**：定义 Codex/Claude 测试场景、变量、对照组和重复策略；
2. **原始交互记录层**：保存官方与中转站的请求、响应、流式事件和环境信息；
3. **统计分析层**：计算重复率、缓存率、延迟分布、字段差异、能力差异和显著性；
4. **结论生成层**：将证据转换为分维度风险评估、置信度和可追溯报告。

核心原则是：**先抓取完整交互，再做官方对照和统计分析；只围绕 Codex 与 Claude；不把文本差异直接等同于掺水。**

## 八、非目标事项

以下内容不应成为项目主要方向：

- 为了覆盖面而加入大量其他模型或工具；
- 仅验证 API 是否能返回一段文本；
- 仅凭单次输出内容判断模型真伪；
- 只做静态模型名称检查；
- 用与 Codex/Claude 无关的测试推断目标中转站的行为；
- 在缺少原始交互和统计数据时给出绝对结论。

## 九、需求意图总结

用户期望的是一个面向实际中转站用户、能够识别“是否掺水”的专业检测工具，而不是一个泛用 API 测试集合。工具应以官方行为为参照，以完整抓包/交互记录为基础，以统计学和缓存率等数据交叉验证，最终提供带证据、带置信度、可复核的判断。
